# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build Commands

```bash
# Assemble debug APK
./gradlew assembleDebug

# Assemble release APK
./gradlew assembleRelease

# Run the game's tests
./gradlew :shared:desktopTest

# Run a single test class
./gradlew :shared:desktopTest --tests "com.osudroid.beatmaps.BeatmapTest"

# Run Android Lint
./gradlew lint
```

Requires **Java 17**, **Android NDK 22.1.7171670** and the **android-36.1** SDK platform (`compileSdk`, `targetSdk` stays 29). The main app depends on Verktex, the engine, which is its own repository (https://github.com/Reco1I/verktex), checked out as a git submodule in `verktex/` and included with `includeBuild('verktex')` (see `verktex/docs/extraction.md` and `verktex/CLAUDE.md`). Clone with `--recurse-submodules`, or run `git submodule update --init` after cloning. A change to the engine is committed and pushed in `verktex/` first, and then the game commits the submodule's new commit. The game depends on it as `com.reco1l.verktex:shared`, and its tasks run from here as `:verktex:<project>:<task>` (or as `:<project>:<task>` with `./gradlew -p verktex`). It needs its own `verktex/local.properties`, which `settings.gradle` copies from the game's when it's missing. Verktex's modules are:

- `:verktex:shared` (`verktex/shared/`): the engine, one Kotlin Multiplatform module with an `android` and a `desktop` target. `src/commonMain/` is everything platform independent and must not depend on Android or the JVM. `src/jvmMain/` is what both platforms share because they run on a JVM. `src/androidMain/` is the Android platform, with its graphics backends and the BASS audio library (`com.un4seen.bass` and its natives), and `src/desktopMain/` the desktop one (OpenGL 3.3 through LWJGL, BASS through JNA), see `verktex/docs/desktop-platform.md`. The built-in shaders and fonts are in `assets/`.
- `:verktex:androidApp` and `:verktex:desktopApp`: Verktex's own applications, the browsers of its UI tests alone (`./gradlew :verktex:desktopApp:run`, `:verktex:androidApp:installDebug`). The game never depends on them.
- `:verktex:android-natives`: what the Android platform needs from the NDK: the native library of the Vulkan backend, and the tasks that compile the shaders to SPIR-V and package the validation layer.
- `:verktex:desktop-natives`: the desktop counterpart: the Vulkan backend's library, built with CMake from `verktex/natives/vulkan/` (shared with Android, Linux x64 so far), and the shaders' SPIR-V, as resources. Desktop starts on Vulkan when the Graphics backend setting is Vulkan (or `--backend Vulkan` in the UI test browsers) and falls back to OpenGL 3.3, see `verktex/docs/plans/vulkan-backend.md`.
- `:verktex:shadertools`: the shader translator, used by the Vulkan backend and by the build.

Engine tests live in `verktex/shared/src/desktopTest/` (the common and desktop ones) and `src/androidHostTest/` (Robolectric), and run with `./gradlew :verktex:shared:desktopTest :verktex:shared:testAndroidHostTest :verktex:shadertools:test`.

The game follows the structure Kotlin recommends for multiplatform projects (https://kotlinlang.org/docs/multiplatform/multiplatform-project-recommended-structure.html): a shared module and one module per application with its entry points, see `docs/multiplatform-game.md`:

- `:shared` (`shared/`): the game itself, Kotlin Multiplatform with the targets of Verktex, `android` and `desktop`. Everything but its Android side is common code, in `src/commonMain/`, which can't depend on Android or the JVM: both targets are JVMs, so the compiler doesn't stop it, and `./gradlew :shared:checkCommonSources` (part of `check` and `desktopTest`) fails on Java imports and the stdlib members only the JVM has. `src/androidMain/` is the Android side of the game that isn't an entry point: `AndroidOsuGameHost`, the platform implementations and the features only Android has so far (the accessibility check), with its resources (`res/`: the launcher and notification icons and the activities' theme). The game has no Android UI: everything is drawn with Verktex. The beatmap listing (`BeatmapListing.show()`) is `BeatmapListingScene` (`com/osudroid/ui/v2/beatmaplisting/`), rewritten on Verktex from upstream's Android view: it searches the selected `BeatmapMirror` (or a `BeatmapSearchSource`, which the UI tests give made up sets) a page at a time in a recycled grid of `BeatmapSetCard`s, streams previews (`BeatmapPreviewPlayer`) and downloads through `BeatmapDownloader`, whose `current` and `imported` it follows. What the game needs from the platform goes through Verktex's `Platform` (clipboard, haptics, file picking, refresh rate…), and what only its hosts provide through `OsuGameHost` (`OsuGameHost.current`), implemented by `AndroidOsuGameHost` (which `MainActivity` extends), `OsuDesktop` and the UI test browsers, with a default for hosts that don't have a feature. Videos are Verktex's `Video`, over the platform's decoder (ExoPlayer on Android, FFmpeg on desktop). Its assets (the default skin, sounds, fonts) are in `shared/assets/`. Its tests are in `src/desktopTest/` (`./gradlew :shared:desktopTest`).
- `:androidApp` (`androidApp/`): the Android application. It has the entry points (`MainActivity`, `PermissionActivity`, `OsuUITestActivity`), the manifest, and what an application decides: its id (`com.reco1l.rimu`, `.debug` for debug and profile builds), its name (rimu!, `rimu!-debug` for debug builds), version, signing and build types (`debug`, `release`, `profile`). Debug and profile builds are signed with each machine's Android debug key (`~/.android/debug.keystore`), release builds with the release key given in `local.properties` (`RELEASE_KEYSTORE`, relative to `androidApp/`, `RELEASE_KEYSTORE_PASSWORD`, `RELEASE_KEY_ALIAS`, `RELEASE_KEY_PASSWORD`), never committed, and unsigned without it. `:shared` is a library with a single variant and no `BuildConfig`, so the activities give the application's build type to Verktex's `Platform.application`. APKs are built in `androidApp/build/outputs/apk/`, named `rimu-<version>-<build type>.apk`.
- `:desktopApp` (`desktopApp/`): the desktop application: `OsuDesktop` and the UI test browser, over the desktop target of `:shared` and of Verktex. Run it with `./gradlew :desktopApp:run`; `--args="--screenshot build/game.png --delay 10"` saves a frame after the delay and exits, and `--quickplay '<beatmap words>' [--no-autoplay]` plays a beatmap once the game starts (`QuickPlay`, debug builds; on Android, `--es quickplay` on `MainActivity`). Its multiplayer connects but is untried, it plays videos with FFmpeg libraries `:verktex:shared:prepareFFmpeg` downloads (see `verktex/docs/desktop-platform.md`), and its database, as Android's, is recreated when its version changes. `./gradlew :desktopApp:distZip` builds a distribution (`bin/rimu`, FFmpeg's libraries for the building platform in `ffmpeg/`, which `OsuDesktop` finds next to `lib/`; it needs a Java 17 runtime), a debug build unless given `-PdesktopVersion` and `-PdesktopBuildType=release`. The **Release** workflow (`.github/workflows/release.yml`, started by hand) builds the signed APK and the Linux and Windows distributions and creates a GitHub release with them.

## Architecture Overview

### Package Structure

The codebase is split across multiple main package roots, each in `shared/src/commonMain/kotlin/` and, for its Android parts, in `shared/src/androidMain/{kotlin,java}/` and `androidApp/src/main/{kotlin,java}/`:

- **`ru/nsu/ccfit/zuev/osu/`** — Legacy code, mostly converted to Kotlin: replays (`scoring/`) and `LibraryManager` are in `:shared`, `MainActivity` (Java, only a launcher) in `:androidApp`. Most subsystems here are singletons.
- **`com/acivev/`** — Vibration and haptic feedback management (`VibratorManager`, `VibratorCheckUtils`, etc.) as well as snow effects (`ui/Effect.kt`).
- **`com/osudroid/replay/`** — Replay imports (`ReplayImporter`, from the settings' file picker). Replays themselves are JSON (`ru/nsu/ccfit/zuev/osu/scoring/ReplayData.kt`, version 10), written gzipped as `.rmr` files (`Replay.FILE_EXTENSION`), apart from osu!droid's `.odr`; the uncompressed JSON ones rimu! wrote before as `.odr`, and the Java-serialized ones before them, upstream's, are still read (`LegacyReplay.kt`) but never written, through java-serialization-kotlinx (`com.github.Reco1I.java-serialization-kotlinx:java-serialization-kotlinx`, https://github.com/Reco1I/java-serialization-kotlinx, published with JitPack), a decoder of Java's object serialization streams and a decode-only kotlinx.serialization format over it, extracted from the game: changes to it go to its repository, released with a tag, and the game updates its version. Opening a replay from another app on Android plays it (`AndroidOsuGameHost`).
- **`com/osudroid/`** — Modern Kotlin code. Contains beatmap parsing, difficulty calculation, the mod system, multiplayer, Room database, and newer UI scenes. Gameplay is in `com/osudroid/game/` (see Game Loop), its objects (`GameObject`, `GameplayHitCircle`, `GameplaySlider`, `GameplaySpinner`, `GameObjectPool` and the `GameObjectListener` they're given) in `game/objects/`, and the statistics of a score (`Statistic`) in `com/osudroid/scoring/`. `docs/plans/gameplay-structure.md` maps the names older plans use (`GameScene`, `GameHelper`, `StatisticV2`) to these.
- **`verktex/`** — The engine. `verktex/src/commonMain/` holds rendering, audio, input, clocks (`time/`) and the UI components (`Component`, `Container`, `Scene`, `Sprite`, etc.). `src/androidMain/` holds the Android platform (`com/reco1l/verktex/android/`) and `src/desktopMain/` the desktop one. The built-in shaders (`shaders/`) and fonts (`fonts/`) are in `verktex/assets/`, which each platform packages.
- **`com/reco1l/framework/`** — Kotlin extensions of existing classes, such as the tolerant iteration of lists.
- **`com/rian/framework/`** — A couple of utility classes such as `RollingNumber`.
- **`shared/src/desktopTest/`** — Unit tests for beatmap parsing, difficulty calculation, and other core logic, with their resources (beatmap files).

### Game Loop

`OsuGame.start` starts the game on every host: the hosts (`AndroidOsuGameHost`, which extends Verktex's `AndroidGameHost` and which `MainActivity` only launches, and `OsuDesktop`) call it once the engine is initialized and give it their platform parts through `OsuGameHost` (e.g. `onGameStarted`, where Android opens the file or the room invite it was opened with). Scenes are kept in a stack through `Verktex.pushScene` and `Verktex.popScene`, and `Verktex.resetScenes` replaces the whole stack (the hosts do it with the main menu once the splash ends). The scene flow for singleplayer is:

```
SplashScene → MainScene (menu hub)
                  ↓
              SongSelect → GameLoaderScene → GameplaySession (gameplay) → ResultsScene (results)
```

The splash shows a loading indicator while the database, the skin and the library (as the database has it, `LibraryManager.loadFromDatabase`) load, then the welcome animation, the menu's rimu! logo growing in at the center, a bit bigger than the menu shows it (`MainScene.SPLASH_LOGO_SCALE`), and the menu: nothing is imported nor scanned before it. The menu's first entrance (`MainScene(playIntro = true)`) continues it: the logo lifts and stamps down to its own scale, the background flashes white and fades to the beatmap's, and the menu expands from behind the logo. Once the menu shows, `LibraryImport.refresh()` brings the library up to date in the background (see Beatmaps & Difficulty).

For multiplayer, the flow is:

```
SplashScene → MainScene (menu hub) → LobbyScene
                                         ↓
                                     RoomScene → GameLoaderScene → GameplaySession (gameplay) → ResultsScene (results)
```

A play starts with `Gameplay().start(PlayRequest(...))` (`com/osudroid/game/`). `Gameplay` is the play and its retries: it shows the loader, loads the beatmap with `PlayLoader` into a `LoadedPlay` (`game/loading/`, reused while the same beatmap and mods are retried), and makes a `GameplaySession` (`game/session/`) for each attempt, which owns the attempt's scene, clock and state and drives the gameplay loop through its parts in `game/session/`: `ObjectSpawner` (objects and follow points), `ReplayInputSource` (a replay's cursors), `CursorPresenter` (cursor sprites, autoplay's cursor, Flashlight), `ControlPointTracker`, `BreakController`, `VideoController`, `MultiplayerSync` and, for seeking a replay, `ScoreReconstruction`; it judges the objects and records the replay. The scoring rules are in `game/rules/` (`ScoreProcessor`, `HealthProcessor`, `HitJudging`), and what the objects depend on of a play (its mods, its timing) is its `GameplayContext`, which they get from their listener. The HUD reads a play through `GameplayState`. Its results are `Gameplay.results`, a `Results` (`com/osudroid/ui/v2/results/`): it shows a score in a `ResultsScene`, whose performance is calculated in the background (`calculateResultsPerformance`), saves it and submits it (`ScoreSubmissionCard`), and in multiplayer lists the match's scores (`ResultsLeaderboard`).

### Rendering

Verktex handles all rendering. UI is a tree of `Component`s measured and laid out through `LayoutConstraints`, animated with transforms for UI, and with `Choreography` for anything on the gameplay clock, whose state depends only on the time so that seeking works. Gameplay and the pause menu are laid out in a space 1280 wide, osu!droid's fixed resolution, through a `ScalingContainer` scaling it to the width of the window: there's no global viewport size. Hit objects, spinners, cursors and Flashlight are placed, drawn and judged in osu!pixels, in `GameplayPlayfield` (`com/osudroid/ui/v2/game/`), which scales the playfield by the height over 480 with osu!droid's rounded 4:3 playfield in its center (rounded as osu!droid rounds it, so it's stretched by less than 0.3%). Positions go between the scene and the playfield through the transformations of the components (`GameplayPlayfield.toPlayfield`), and `visibleArea` is the part of the playfield the screen shows. What isn't a hit object but is in the playfield was made for osu!droid's 1280x720 screen and is scaled by `Playfield.SCREEN_PIXEL` (`com/osudroid/game/Playfield.kt`, with the playfield's dimensions). The HUD and the break and countdown screens stay in the 1280 wide space. Scenes don't draw the beatmap's background: `BeatmapBackground` (`com/osudroid/ui/v2/`) is the engine's background (`Verktex.background`, drawn behind every scene), installed when the menu first shows; it follows `BeatmapSelection` with a crossfade, each scene sets how bright it is when entered (`fadeBrightness`), and gameplay dims it and shows a video over it. A crossfade under a lowered brightness shows the old texture through the new one, so scenes where the selection changes keep it at full brightness and dim it with a box of their own (song select's `backgroundDim`). Each scene animates its own entrance in `onEnter`, every time it shows: its top bar slides down, its content rises and its bottom bar slides up, staggered (OutCubic, 0.4s fades and 0.55s moves; song select slides its sides in from their edges, a whole window width away while fading in, in 0.4s with OutQuart), while the background stays still. Hit objects (`GameObject`) are Containers filling their layer and owning their pieces, as osu!lazer's `DrawableHitObject`s; `GameplaySession` drives their judgement (`updateJudgement`). The playfield's layers are `spinners`, `underlay`, `objects`, `approachCircles`, `judgements` and `cursors`: pieces drawn above every object (approach circles, slider balls and follow circles) are drawn in `approachCircles` through Verktex `Proxy`s (`GameObject.drawIn`). Objects show their own judgements (`GameObject.showJudgement`: the `JudgementPiece`, its hit lighting and particles, and the bursts), from the texture `GameObjectListener` returns, and live until those effects end. Their pieces come from the skin, component by component (`SkinPieces`, `com/osudroid/ui/v2/skin/`): from the texture skin when it has the component's textures (`LegacySkin`), otherwise from the default skin drawn in code (`DefaultSkin`), through the contracts of `skin/Pieces.kt`; see `docs/plans/default-skin.md`. Cursor events carry both positions, and replays store and play back osu!pixels. Slider bodies are Verktex `PathShape`s, a `Path` stroked from a mesh kept on the GPU, in osu!pixels inside the playfield.

A Vulkan backend roadmap lives in `verktex/docs/plans/vulkan-backend.md`. How the frame rate is capped on each platform, and the pending work on it, is in `verktex/docs/plans/frame-rate.md`. Textures and shader outputs are premultiplied, and the atlas keeps a gutter around each region; how, and what's left, is in `verktex/docs/plans/texture-blending.md`. Shaders share code through `#import`, and `ClipMode` follows a component's corner radius, rotation and skew, clipped in the shaders; see `verktex/docs/plans/shaders.md`.

### UI Tests

Verktex's abstract `UITestActivity` (`verktex/.../android/`) and `UITestApplication` (`verktex/.../desktop/testing/`) browse `UITestSuite`s (`verktex/.../testing/`) to try components in isolation; `VerktexUITests` covers the engine components, and the engine's repository has the run configuration of its own desktop browser (`./gradlew :verktex:desktopApp:run` from here). The game's suites (`OsuUITests`, `OsuSceneUITests`, `OsuGameplayUITests`) are in `:shared` (`com/osudroid/ui/v2/test/`), with `TestGameContext` standing in for the game. Each browser has a run configuration:

- **rimu!: UI Tests (Android)**: `:androidApp`'s `OsuUITestActivity`, every suite, Verktex's included.
- **rimu!: UI Tests (Desktop)**: `./gradlew :desktopApp:runUITests`, every suite, Verktex's included.
- **rimu!: Verktex UI Tests (Desktop)**: `./gradlew :verktex:desktopApp:run`, Verktex's browser alone. The engine's own **Verktex: UI Tests (Desktop)** runs `:desktopApp:run` from the project's root, so it only works with `verktex/` opened on its own: from the game, it opens the game.

The Android browser is enabled only in debug and profile builds and runs in its own process. Open a test directly with:

```bash
adb shell am start -S -n com.reco1l.rimu.debug/com.osudroid.ui.v2.test.OsuUITestActivity --es test "'osu!/Hit circles'"
```

Add `--es backend <name>` (a `GPUBackend`: `OpenGLES3`, `OpenGLES2`, `Vulkan`) to open it with another graphics backend.

On desktop, `--test` opens a test and `--screenshot <file.png>` saves a frame and exits. The desktop window has no safe area, so the browser simulates a phone's, with its toolbar button or `--safe-area <name>` (a `SimulatedSafeArea`, cutouts on the sides: `None`, `CutoutLeft`, `CutoutRight`, `CutoutBoth`): it's the window's safe area while the browser is shown, so code reading `Verktex.graphics.window.insets` sees it too. Relative paths resolve against the root of the build the task belongs to, so Verktex's browser saves under `verktex/`:

```bash
./gradlew :verktex:desktopApp:run --args="--test 'Verktex/Text' --screenshot build/text.png"
./gradlew :desktopApp:runUITests --args="--test 'osu!/Hit circles' --screenshot build/hit-circles.png"
```

The game itself runs with **rimu!: Game (Android)** and **rimu!: Game (Desktop)** (`./gradlew :desktopApp:run`).

### Asset / Resource Loading

`SkinTextures` and `SkinSounds` look up skin assets, preferring the beatmap skin, then the custom skin folder, then the default skin. Gameplay and the HUD have no default textures: a piece a skin has no textures for is drawn in code by `DefaultSkin` (`com/osudroid/ui/v2/skin/`, modelled on osu!lazer's Argon), and `gfx/` keeps the textures of the menus and the pause, fail, break, skip and countdown screens. Mod icons (`ModIcon`) have no default textures either: they're the skin's `selection-mod-*` texture when it has one, otherwise a Font Awesome glyph (`modIconGlyph`) over the mod's acronym. The results (`ResultsScene`) use no textures: the rank is text with Verktex's text effects. `Skin` loads the configuration of a skin folder. Textures and sounds go through Verktex's `Textures` and `Sounds`, in named stores (`Textures.store(name)`, `Sounds.store(name)`; the default one when none is given) unloaded all at once: the skin's (`skin`), the beatmap skin's (`beatmap-skin`), downloads (`cache`) and backgrounds (`backgrounds`). A skin change unloads the `skin` stores, so a component outliving it refers to a skin texture through a lookup (`skinTexture(name)`, `skinFrames(name)`), never a region it was given. The skin loads lazily: the menus load what they show, mod icons load when the ModMenu builds them, and a play's textures and sounds load while it loads (`SkinTextures.preloadGameplay`, `SkinSounds.preloadGameplay`). The game's own assets (the default skin, sounds, fonts) are in `shared/assets/`, which Android packages as assets and desktop loads from the classpath.

Text goes through Verktex's `Localization` (`verktex/shared/.../localization/`). `:shared:generateStringResources` turns the language pack into `strings/<locale>.json` assets and the generated `Res`, whose `Res.string.*` are `LocalizedString`s: a `CharSequence` that components such as `Text` show in the current language and re-resolve when it changes. Format one with `Res.string.x.format(args)`, and use `toString()` where a `String` is needed. The language pack is osu!droid's: the strings that name the game (`brandedStrings` in `shared/build.gradle.kts`) say rimu! instead in every language, also as Android resources for the manifest's labels, and `shared/strings/strings_rimu.xml` replaces the English strings rimu! words differently; the ones naming osu!droid's server, website, folder or star rating keep it.

### Audio

Through Verktex's audio API: its driver (`Verktex.audio`) opens samples and streams (`createSampleSource`, `createStreamSource`). On Android the audio backend is a setting (Audio → Output, Verktex's `VerktexSettings.AudioBackend`, applied on the next start): BASS, bundled in Verktex, or the experimental Oboe, over Verktex's native audio core, which falls back to BASS where it can't start and whose stream positions, as BASS's, don't subtract the output's latency (hitsounds would be late against the music), see `verktex/docs/plans/audio-backends.md`. Desktop has BASS alone. `MusicService` (`com/osudroid/audio/`, reached through `OsuGame.music`) plays songs and knows their beatmap, and `BassSoundProvider` plays sound effects, whatever the backend. Song select plays previews (`MusicService.playPreview`, faded in by the scene): a song with a `previewTime` starts over there when it ends instead of stopping or playing the next. `GameLoaderScene` takes the preview out of the service (`detach`, given back with `attach` when the play is left) so it keeps playing while the play loads its own song, through the tunnel effect of osu!lazer's player loader (Verktex's `AudioStream.lowPassCutoff`/`highPassCutoff`), and fades it out as gameplay starts.

### Beatmaps & Difficulty

Beatmap files are parsed in `com/osudroid/beatmaps/`. `BeatmapDownloader` (`com/osudroid/beatmaplisting/`) downloads a set from the selected mirror into the cache directory and imports it. Beatmap set (`.osz`) and skin (`.osk`) archives are extracted by `LibraryImport` (Okio's `openZip`), from the game's folders, the device's downloads folder (Verktex's `PlatformStorage.downloadsDirectory`) or a file the game was opened with, on both platforms; `LibraryManager` then scans the beatmaps folder into the database. Both run in the background through `LibraryImport.refresh()`: one refresh at a time behind a mutex (a refresh of the whole library asked while one waits is that one), started as the menu shows, by Solo and Multi, and for a file the game was opened with; it imports the skins and beatmap sets found, resets the outdated star ratings (first refresh only), scans the folders the database lacks, loads the library, which starts the difficulty calculation, and reloads song select, the menu's music and a multiplayer room's beatmap. Downloads import through `LibraryImport.importDownloaded`, behind the same mutex, and `awaitIdle()` waits for them all (QuickPlay does). Extracting archives is listed in the `NotificationCenter` while it runs, without popping up, and a refresh posts one notification of what it imported (naming it when it's a single beatmap set or skin); scanning is silent, but for the folders kept without a beatmap that loads.

### Notifications

`Notifications` (`com/osudroid/notifications/`) are what the game tells the player outside of a scene: messages (`post`, optionally with a button) and background tasks (`startTask`, then `complete`/`fail`, with a progress and a button), from any thread. A message pops up as one of Verktex's `Toasts`, and so does a task when it ends and, unless started with `showToast = false`, when it starts; a task dismissed (`dismiss`) goes away without telling anything, as the difficulty calculation does when it ends; its progress only shows in the `NotificationCenter` (`com/osudroid/ui/v2/notifications/`, its rows `NotificationRow`s, a `Toast` with a progress and a button), which lists them (up to `MAX_ENTRIES`), opened from the bell of the main menu, which counts the tasks running or else the unread ones. The library refresh, the difficulty calculation, downloads, replay imports and connection failures report there. Verktex's `Toasts` are messages alone (a text, an optional title): one shows at a time, the others queued in order (one already shown or waiting isn't queued again), and the user can close or swipe them away. They're compact, to cover little of a phone's screen. Difficulty calculation (star rating and PP) lives in `com/osudroid/difficulty/` and implements both the osu!droid and osu!standard algorithms. `BeatmapDifficultyCalculator` is the main entry point.

### Mod System

Mods are defined in `com/osudroid/mods/`. Each mod implements modifier interfaces and can alter difficulty attributes, hit windows, and gameplay behavior. `ModCombination` aggregates active mods.

### Data Persistence

Room database accessed via `DatabaseManager`, kept in the application's private folder (Verktex's `PlatformStorage.dataDirectory`: Android's `filesDir`, `~/.local/share/rimu` or `%APPDATA%\rimu` on desktop) as the settings are. The database (`OsuDatabase`), its DAOs and entities are common code under `com/osudroid/data/`, generated by Room's KSP for each target, and opened in common code over the bundled SQLite (`DatabaseManager.open`, or `openInMemory` for tests and the UI test browsers), with a builder per platform (`osuDatabaseBuilder`). Verktex doesn't provide databases: they belong to each project that needs one. DAO functions suspend, as Room only implements those outside Android: call them from coroutines (`async {}`, then `updateThread {}` for the UI). This project is separate from upstream osu!droid: there are no migrations, and a database of another version (`DATABASE_VERSION`) is recreated. Nothing is imported from upstream's data either (its old database, its preferences).

Settings go through Verktex's `Settings` (`verktex/shared/.../settings/`), a typed store saved as `settings.json` in the data directory. Each setting is a `SettingKey` (`setting(name, default)`), read with `Settings[key]` and written with `Settings[key] = value`. The engine's are in `VerktexSettings`, the game's in `OsuSettings` (`com/osudroid/settings/`), with helpers for the ones read in other units (e.g. `OsuSettings.musicVolume`). The folders are in `GameFolders` and `SkinFolders`: the game's folder is `osu!droid/` by default, shared on purpose with osu!droid, so it only keeps what the player handles (beatmaps in `Songs/`, skins in `Skin/`, replays in `Scores/`, the settings' backup `rimu.cfg`).

### Multiplayer

Socket.IO for real-time room events, through `KtorRoomSocket`: a Socket.IO v4 client over Ktor WebSockets, in common code (`KtorRoomSocketTest` runs against a server given with `-PsocketIoTestUrl`). HTTP requests go through Ktor: Verktex's `Network` creates clients over Ktor's default engine (found on the classpath: OkHttp, brought by the platform modules), and the game's `httpClient` (`com/osudroid/online/HttpClient.kt`) is one over it with content negotiation: requests use Ktor directly (`httpClient.get(url) { parameter(...) }.body<T>()`) with `@Serializable` responses read leniently whatever their content type, and unsuccessful responses throw. `downloadTo` streams a download with progress. They're called from coroutines such as `async {}` blocks. Multiplayer logic lives in `com/osudroid/multiplayer/`.

## Key Conventions

- New gameplay/beatmap/difficulty code goes in `com/osudroid/` (Kotlin).
- Generic UI components belong in Verktex's `commonMain`, and game-specific ones in `com/osudroid/ui/v2/` (Kotlin).
- Each scene handles the back key in its `onInputEvent`, once its components didn't consume the event (`event is KeyboardEvent && event.isBackPress`: Android's back button or Escape). On Android a back press no scene consumes finishes the activity.
- Verktex never depends on the game, and its `commonMain` never depends on Android or the JVM (including `org.json`, which ships with the Android SDK). What it needs from a platform is expected there and actual in each target's source set, as `Platform` is (an `expect object`, attached to its host by `AndroidGameHost` and `DesktopGameHost`); interfaces are kept for what has several implementations on one platform (`Renderer`, `AudioDriver`, `Logger.Implementation`). Everything else comes from multiplatform libraries; see `verktex/docs/extraction.md`. It is a separate repository: its build never refers to the game's, its versions are in `verktex/gradle/libs.versions.toml`, and nothing in it may read the game's files.
- Legacy Java files in `ru/nsu/ccfit/zuev/osu/` are modified in-place; avoid moving them. They're in `shared/src/androidMain/java/` and `androidApp/src/main/java/`, apart from the Kotlin sources in `kotlin/`.
- `:shared` is a library with a single variant: it has no `BuildConfig`. What depends on the application (its id, its build type, whether it's a debug build) comes from Verktex's `Platform.application`, whose build type the activities of `:androidApp` give from its `BuildConfig`, and what depends on a build type is declared by `:androidApp`.
- Entry points go in the application modules, and nothing in `:shared` names them: it reaches the Android activity as Verktex's host (`Verktex.host`, an `AndroidOsuGameHost`).
- Game code goes in `:shared`'s `commonMain`, never depending on Android or the JVM: files through Okio (`Platform.fileSystem`), dates through kotlinx-datetime, numbers through `formatString`/`formatNumber` (not `String.format`), time through `kotlin.time` (`currentTimeMillis()` for the wall clock), locks and atomics through atomicfu and `kotlin.concurrent.atomics`, background work through coroutines. What any platform could do goes through Verktex's `Platform`; what's specific to the game's hosts through `OsuGameHost`, with a default for hosts that don't have it.
